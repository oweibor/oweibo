### * **`oweibo_desktop_tool`**

1. The "My Computer" hybrid experience — local files, terminal, native app control, desktop app bridge. It requires a local daemon running on the user's machine, a secure bidirectional channel between that daemon and the cloud agent, file-system namespace sandboxing, process execution sandboxing, and GUI automation via accessibility APIs. That is a separate `DesktopTool` implementation plan, following exactly the same structure as the BrowserTool unified plan: its own package, its own `IBrowserBackend`-equivalent interface, its own Vault namespace, its own trust gates, its own rollout phases. The BrowserTool plan already formally deferred it in §17 Phase 10 and specified the handoff design. The right next step is a new `oweibo_desktop_tool_implementation_plan_v1.0.md`, not edits to v9.4.4. The only surgical edit v9.4.4 would eventually need is a single line in `GeneralAssistOrchestrator` to route file-system tasks to `DesktopTool` — and that can be specified as a surgical edit inside the DesktopTool plan itself, identical to how the BrowserTool plan specified its orchestrator edits.

2. The plan is self-correcting (within tasks) and self-improving (across tasks at the tool-selection and strategy-recall level), but it is not self-extending — it can't detect a capability gap and autonomously build a new scaffold to close it. That's the specific Karpathy-loop behaviour
